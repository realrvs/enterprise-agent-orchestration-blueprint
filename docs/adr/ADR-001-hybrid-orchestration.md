# ADR-001: Hybrid Orchestration Core

## Context

Крупные корпорации с территориально распределённой структурой и сложными
бизнес-процессами (закупки, экспертиза, согласования) сталкиваются с
фундаментальной проблемой: монолитные системы управления процессами
не способны адаптироваться к изменениям ЛНА, законодательства и
бизнес-требований с нужной скоростью.

Каждое изменение регламента требует:
- Доработки кода (недели-месяцы).
- Тестирования.
- Повторного развёртывания.

При этом современные задачи требуют **семантической обработки**
неструктурированных данных (документы, заявки, жалобы), которую
невозможно реализовать чисто детерминированными правилами.

Существуют два полярных подхода:

1. **Чистый BPMN** (Camunda, Temporal) — детерминированный,
   аудируемый, но негибкий. Каждое новое правило → доработка.

2. **Чистые LLM-агенты** (LangGraph, CrewAI, AutoGen) — гибкие,
   адаптивные, но недетерминированные. Нет гарантий выполнения,
   сложно аудировать, высокий риск галлюцинаций в критичных
   решениях (финансовых, юридических).

Ни один из подходов в чистом виде не решает задачу enterprise-уровня.

## Decision

Принимаем **гибридную архитектуру оркестрации**, где:

- **Camunda 8 (BPMN)** отвечает за **детерминированный каркас**:
  - Управление состоянием процесса (state machine).
  - Таймауты, retry-политики, компенсации (Saga-паттерн).
  - Human-in-the-loop (User Tasks, Tasklist).
  - Аудит каждого шага (Operate, Process Mining).
  - Транзакционность и гарантии выполнения.

- **LangGraph (LLM-агенты)** отвечает за **семантическую работу
  внутри шага**:
  - Анализ неструктурированных данных (документы, заявки).
  - Классификация, извлечение сущностей, RAG.
  - Формирование рекомендаций (Recommendation DTO).
  - Выбор инструментов (tool calling).

**Граница ответственности** между BPMN и агентом проходит по
принципу: **детерминированные и критичные решения — BPMN,
семантические и вероятностные — LLM**.

Ключевое ограничение: **LLM-агент не вызывает бизнес-функции напрямую**.
Он формирует `RecommendationDTO`, который проходит через
**Policy Enforcement Point** (в BPMN-слое) с проверками:
- RBAC (SVID агента в allow-list).
- Confidence threshold (≥ 0.85 для автономного выполнения).
- Tool allow-list (только разрешённые действия).
- Append-only audit log.

## Consequences

### Положительные

- **Адаптивность:** изменение ЛНА → обновление промпта агента
  (дни, а не месяцы).
- **Аудируемость:** все решения агента логируются с reasoning
  и confidence, каждое действие проходит через BPMN-шаг.
- **Безопасность:** агент не может вызвать опасное действие —
  только рекомендовать, а Policy Enforcement Point решает.
- **Надёжность:** BPMN гарантирует выполнение процесса даже
  при сбое агента (retry, эскалация на человека).
- **Human-in-the-Loop:** критичные решения (суммы > X, низкая
  уверенность) автоматически эскалируются.

### Отрицательные / Риски

- **Сложность:** два движка (Camunda + LangGraph) → два
  контура деплоя, мониторинга, отладки.
- **Latency:** LLM-вызовы добавляют 1–5 секунд на шаг.
- **Стоимость:** inference LLM может быть значимым при больших
  объёмах (митигация: кэширование, маршрутизация на SLM).
- **Компетенции:** команда должна знать и BPMN, и LLM-стек.

### Митигации

- **Сложность:** единый контур observability (Langfuse + Operate).
- **Latency:** async-обработка, кэширование частых запросов.
- **Стоимость:** LLM Router (маршрутизация на дешёвые модели).
- **Компетенции:** обучение команды, найм гибридных специалистов.

## Alternatives Considered

### Альтернатива 1: Чистый BPMN (Camunda 8 без LLM)

**Плюсы:** простота, детерминизм, полный аудит.

**Минусы:** негибкость, каждая новая семантическая задача требует
разработки кода, невозможно обрабатывать неструктурированные данные.

**Отвергнуто:** не решает задачу адаптивности к изменениям ЛНА.

### Альтернатива 2: Чистые LLM-агенты (LangGraph без BPMN)

**Плюсы:** максимальная гибкость, адаптивность, естественная
работа с неструктурированными данными.

**Минусы:**
- Нет гарантий выполнения (агент может «застрять» в цикле).
- Нет аудита (что именно решил агент и почему).
- Нет управления состоянием (state machine).
- Нет Human-in-the-Loop (нужно строить вручную).
- Высокий риск галлюцинаций в критичных решениях.

**Отвергнуто:** неприемлемо для enterprise-уровня в
высокорегулируемых отраслях.

### Альтернатива 3: Temporal + LangGraph

**Плюсы:** Temporal мощнее Camunda в части долгоживущих транзакций
(arbitrary code, версионирование workflow).

**Минусы:**
- Temporal не имеет нативного BPMN-редактора и UI для бизнеса.
- Human-in-the-Loop требует ручной реализации.
- Меньше готовых интеграций с enterprise-системами (ЕИС, ЭТП).

**Отвергнуто:** Camunda даёт BPMN-стандарт, Web Modeler и
Tasklist из коробки — критично для бизнес-пользователей.

### Альтернатива 4: Camunda 8 + отдельный микро-сервис для LLM

**Плюсы:** агент полностью изолирован, управляется независимо.

**Минусы:** дублирование логики state management, сложнее
поддерживать границу транзакции между BPMN и агентом.

**Отвергнуто:** LangGraph как воркер Zeebe (через pyzeebe) даёт
более чистую интеграцию — job activation и переменные
процесса работают «из коробки».
